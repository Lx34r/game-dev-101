# 3D 数学基础：坐标空间、变换与游戏渲染管线

<ArticleTags />

3D 数学最容易学成公式清单：点乘、叉乘、矩阵乘法、四元数。真正写游戏时，问题往往不是“公式忘了”，而是**不知道当前在哪个坐标空间、变换顺序对不对、法线该不该用同一个矩阵**。

这篇笔记把《3D 数学基础：图形与游戏开发》中的坐标空间、矩阵变换、旋转表示、几何检测与渲染管线串成一条工程路径，并列出能直接排查的陷阱。

## 1. 先问：现在在哪个空间？

同一个位置在不同坐标空间里有不同数值。游戏里常见的空间：

| 空间 | 原点/轴 | 典型用途 |
| - | - | - |
| 模型/物体空间 | 模型自身原点 | 美术制作、局部动画 |
| 世界空间 | 场景全局原点 | 物理、AI、关卡逻辑 |
| 摄像机空间 | 摄像机位置与朝向 | 视图变换、裁剪 |
| 惯性空间 | 物体位置 + 世界轴 | 物体局部旋转、平移分离 |
| 屏幕/NDC | 视口 | UI、后处理、拾取 |

“位置不对”时，先确认三件事：

1. 这个数值属于哪个空间？
2. 目标空间是什么？
3. 中间经过了哪些变换，顺序是什么？

嵌套坐标系（父子层级）会把这些变换串起来：子物体的世界变换 = 父世界变换 × 子局部变换。层级越深，越要避免在错误的层级里直接改世界坐标。

## 2. 左手系与右手系

左手系与右手系决定叉乘方向、旋转正方向和摄像机朝向。Unity 使用左手坐标系，许多图形 API/数学教材使用右手系。

跨引擎/跨资料时，必须先统一：

- 哪个轴向上？（Unity 是 Y-up）
- 正面朝向是 +Z 还是 -Z？
- 旋转正方向从哪个轴看向哪个轴？
- 叉乘结果指向哪边？

不要在不同约定之间“凭感觉”转换。写一个最小的坐标轴测试场景，把 X/Y/Z、正面、上方画出来，比在代码里猜更可靠。

## 3. 点、向量与法线

- **点**表示位置，受平移影响；
- **向量**表示方向/位移，不应受平移影响；
- **法线**是方向，但在非均匀缩放下不能用普通模型矩阵变换。

点乘用于投影、夹角、背面判断；叉乘用于求法线、构建正交基、判断左右。一个常见错误是把点当向量做平移，或者把法线当普通向量乘模型矩阵。

法线的正确变换通常是模型矩阵的**逆转置矩阵**：

```csharp
Matrix4x4 normalMatrix = modelMatrix.inverse.transpose;
Vector3 worldNormal = normalMatrix.MultiplyVector(localNormal).normalized;
```

非均匀缩放会让法线不再垂直于表面；逆转置是修正这一点的手段。

## 4. 矩阵：顺序与约定

矩阵乘法不满足交换律。`A × B` 表示先应用 B，再应用 A（列向量约定下）。Unity 的 `Matrix4x4` 使用列向量，`M.MultiplyPoint(p)` 等价于 `M * p`。

一个常见的变换组合：

```csharp
Matrix4x4 model =
    Matrix4x4.TRS(position, rotation, scale);

Vector3 world = model.MultiplyPoint3x4(localPosition);
Vector3 worldDir = model.MultiplyVector(localDirection);
```

需要记住：

- 平移只对点生效，对方向不生效；
- 缩放、旋转、平移的顺序会改变结果；
- 行向量与列向量约定不同，转置关系要统一；
- 4×4 齐次矩阵用于把平移纳入线性变换；
- 透视投影不是仿射变换，它会产生 w 分量，之后要做透视除法。

## 5. 旋转的三种表示

| 表示 | 优点 | 缺点 |
| - | - | - |
| 矩阵 | 可直接变换向量、易与渲染管线结合 | 占空间、插值困难、正交化误差 |
| 欧拉角 | 直观、适合编辑器/输入 | 万向锁、顺序依赖、插值不自然 |
| 四元数 | 无万向锁、插值平滑、组合方便 | 抽象、双倍覆盖、需归一化 |

选择建议：

- 运行期姿态：优先存四元数；
- 批量顶点/骨骼变换：矩阵；
- UI 上的角度输入：欧拉角作为输入层，提交前转四元数；
- 插值：四元数 Slerp，并处理 `q` 与 `-q` 的最短路径。

三种表示之间可以互转，但每次转换都可能引入约定差异。统一项目的旋转约定，比在代码里到处转换更重要。

## 6. 几何图元与相交检测

游戏里大量逻辑最终落到“点是否在区域内”“射线是否命中”“两个包围盒是否重叠”。

常用图元：

- 射线：`P(t) = O + tD`；
- 球：`|P - C| <= r`；
- AABB：三轴区间；
- 平面：`n·P + d = 0`；
- 三角形：重心坐标、法线、面积。

射线与 AABB 的 slab 检测：

```csharp
bool RayAabb(Vector3 origin, Vector3 dir, Bounds box, out float t)
{
    t = 0f;
    float tMin = 0f, tMax = float.PositiveInfinity;
    for (int axis = 0; axis < 3; axis++)
    {
        float o = origin[axis], d = dir[axis];
        float min = box.min[axis], max = box.max[axis];
        if (Mathf.Abs(d) < 1e-6f)
        {
            if (o < min || o > max) return false;
            continue;
        }
        float t1 = (min - o) / d;
        float t2 = (max - o) / d;
        if (t1 > t2) (t1, t2) = (t2, t1);
        tMin = Mathf.Max(tMin, t1);
        tMax = Mathf.Min(tMax, t2);
        if (tMin > tMax) return false;
    }
    t = tMin;
    return true;
}
```

射线与三角形常用 Möller–Trumbore；实现时要统一背面剔除规则、epsilon 与坐标系手性。先用 AABB/球做粗筛，再做三角形/网格精确检测，是常见的性能分层。

## 7. 渲染管线的空间链

```mermaid
flowchart LR
  A["模型空间"] --> B["世界空间"]
  B --> C["摄像机空间"]
  C --> D["裁剪空间"]
  D --> E["NDC"]
  E --> F["屏幕空间"]
```

- 模型矩阵：局部 → 世界；
- 视图矩阵：世界 → 摄像机；
- 投影矩阵：摄像机 → 裁剪；
- 透视除法：裁剪 → NDC；
- 视口变换：NDC → 屏幕。

相机常用“look-at”构建视图矩阵：由位置、目标、上方向得到一组正交基，再求逆。相机的上方向不能与视线平行，否则基退化。

裁剪空间、NDC 与平台差异（Y 轴方向、深度范围）也是常见 bug 来源。跨图形 API 时，投影矩阵与深度约定要显式处理，不要假设所有平台一致。

## 8. 可见性与空间分割

渲染前先剔除不可见对象：

- 视锥剔除：用包围球/AABB 与视锥平面测试；
- 遮挡剔除：PVS、portal、硬件 occlusion query；
- 空间分割：网格、四叉树/八叉树、BSP。

这些结构的共同目标是把“全场景测试”降为“少量候选测试”。选择依据是场景规模、动态对象比例与构建成本，而不是教科书上的“最优结构”。

## 9. 游戏逻辑中的常见应用

- **角色朝向**：四元数/矩阵旋转，避免用欧拉角累积；
- **相机控制**：yaw/pitch 输入 + 四元数或矩阵组合；
- **射线拾取**：屏幕点 → 射线 → 世界空间检测；
- **碰撞/触发**：AABB/球粗筛 + 精确形状；
- **法线/光照**：逆转置变换法线，统一空间后再点乘；
- **动画/骨骼**：局部变换层级组合，注意绑定姿势与逆绑定矩阵。

## 10. 常见陷阱清单

- 角度制与弧度制混用；
- 左手系/右手系、Y-up/Z-up 混用；
- 行向量/列向量约定混用；
- 变换顺序写反；
- 把点当方向做平移；
- 非均匀缩放后仍用模型矩阵变换法线；
- 四元数未归一化或未处理双倍覆盖；
- 欧拉角累积导致万向锁；
- 用屏幕坐标直接做世界空间检测；
- 透视投影后忘记透视除法；
- AABB 变换后没有重新计算包围盒。

## 11. 工程检查清单

- 项目是否明确约定手性、上方向、正面朝向？
- 每个位置的坐标空间是否可追踪？
- 变换组合顺序是否有统一封装？
- 法线是否使用逆转置矩阵？
- 旋转是否优先存四元数，欧拉角只作输入/显示？
- 插值是否处理最短路径与小角度？
- 相交检测是否有粗筛/精确两层？
- 相机基是否避免退化？
- 跨平台投影/深度约定是否验证？
- 是否为坐标转换写了最小可视化测试？

3D 数学的难点不是记住公式，而是建立“空间—变换—约定”的追踪能力。只要每一步都知道自己在哪个空间、用了什么约定、变换顺序是什么，大多数“玄学 bug”都会变成可复现的几何问题。
