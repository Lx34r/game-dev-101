# 人月神话：加人为何越加越慢

<ArticleTags />

“这个版本要延期了，再加几个人吧。”这句话在软件项目里出现了五十年，也仍然在游戏项目里反复出现。Frederick P. Brooks 在《人月神话》里给出的回答很直接：**向已经延期的项目加人，通常只会让它更延期**。

这篇笔记把书里的核心观点放回游戏开发：为什么人月不是可互换的单位、沟通成本如何吞掉人力、概念完整性为什么需要一个人负责、第二系统效应如何毁掉续作，以及 20 周年纪念版里作者自己修正了什么。

::: warning 关于本文
本文依据《人月神话》20 周年纪念版的目录、关键章节与公开资料整理，**不是译文**；对书中观点的引用均为转述，不虚构原书引语。
:::

::: tip 怎么读
如果你在做项目管理，先读第 1、6、7 节；如果你在带设计/技术团队，先读第 3、4 节；如果你正在经历“加人反而更慢”，直接看第 8 节检查清单。
:::

## 1. 人月不是单位：为什么加人会更慢

### 1.1 布鲁克斯法则

书里最著名的一条法则可以概括为：**向进度落后的软件项目增加人力，只会让它更晚**。

原因不是“新人不够聪明”，而是软件任务的性质：

- 任务之间存在前后依赖，不能无限拆分。
- 新人需要学习项目、工具、代码与领域知识，短期内是净负产出。
- 人越多，沟通路径越多，协调成本越高。
- 晚期项目的关键路径往往在集成、调试与决策，而不是“人手不够”。

游戏项目还多一层：程序、策划、美术、音频、QA 之间的沟通需要翻译，信息在跨职能传递中会失真。

### 1.2 沟通成本不是线性的

n 个人两两沟通的路径数是 `n(n-1)/2`：

```mermaid
flowchart LR
    A["3 人 / 3 条"] --> B["6 人 / 15 条"] --> C["12 人 / 66 条"]
```

人翻倍，沟通路径接近四倍。每个新增成员都要与现有成员对齐目标、接口、风格、进度与决策；这些对齐不是“开会十分钟”，而是持续消耗注意力。

### 1.3 游戏项目里哪些任务能并行

不是所有任务都不能加人。关键是区分“可独立并行”与“强耦合/需要统一判断”的工作：

| 任务 | 可并行性 | 加人效果 |
| - | - | - |
| 独立美术资产 | 较高 | 产能上升，但风格/集成/返工成本也上升 |
| 独立关卡内容 | 中等 | 需要工具、规范与设计一致性 |
| 核心引擎/架构 | 低 | 接口与概念一致性要求高，加人易冲突 |
| 战斗手感/系统平衡 | 低 | 依赖反复试玩与统一判断 |
| QA/本地化 | 较高 | 适合并行，但通常在后期才需要 |
| 内容集成/打磨 | 低 | 关键路径，加人容易增加协调负担 |

所以“加人”不是绝对错误，而是**要加在可并行、低耦合、能独立验收的任务上**；加在晚期关键路径上，通常适得其反。

## 2. 乐观主义与估算：为什么总是延期

### 2.1 一切正常的概率

书里指出，大型项目包含大量任务，某些任务还有前后顺序；每个任务“按时完成”的概率都不是 100%，乘起来，“一切正常”的概率会变得很小。

游戏项目尤其乐观：玩法要“好玩”、美术要“惊艳”、性能要“稳定”、剧情要“感人”，每一项都难以在前期准确估算。于是排期往往建立在“所有事情都顺利”的假设上。

### 2.2 90% 完成综合征

“已经完成 90% 了”是项目里最危险的一句话。剩下的 10% 往往包含集成、打磨、边界情况、性能优化、平台适配与 QA 返工——这些才是大头。

游戏开发的“完成”需要定义清楚：

- **功能完成**：代码能跑，但没有内容/平衡/打磨。
- **内容完成**：所有关卡/资产到位，但未整体联调。
- **特性完成**：所有功能冻结，进入稳定性阶段。
- **发布完成**：通过认证、性能、兼容性与 QA。

没有“完成定义”，里程碑就只是日历上的日期。

### 2.3 祸起萧墙：被藏起来的延期

书里用“祸起萧墙”形容进度问题被掩盖：每个团队都说“其他部分会赶上”，于是小延迟被扫到地毯下面，直到某天变成灾难。

游戏项目的典型信号：

- 某个系统一直“快好了”，但从不进入可玩版本。
- 演示只展示精心挑选的片段，不展示集成后的真实状态。
- 风险清单上全是“低风险”，但没人敢打包票。
- 里程碑只检查“有没有做”，不检查“能不能玩”。

## 3. 概念完整性：一个人做决定，团队来实现

### 3.1 概念一致性

书里强调“概念完整性”：一个系统应该像一个人设计出来的，而不是委员会拼出来的。概念一致性比“每个局部都最优”更重要，因为用户感知到的是整体。

游戏项目里，这通常落到创意总监/主设计师/技术负责人身上：谁来拍板核心体验、视觉风格、操作手感、叙事语气？如果每个人都加一点自己的想法，最后会得到一款“每个功能都合理、整体不好玩”的游戏。

### 3.2 外科手术队伍

书里提出“外科手术队伍”的比喻：一个主刀医生负责核心设计与实现，其他人提供支持（助手、工具、测试、文档、行政），而不是让十个医生同时开刀。

这不是说团队只需要一个人，而是说**核心决策要集中，支持工作要分工**。游戏项目里的“核心小组 + 支持团队”很接近这个结构：主创/主程/主美定义方向，内容/工具/QA/外包提供规模化支持。

### 3.3 设计委员会的反例

“设计委员会”听起来民主，但常常导致：

- 每个成员都要在自己的领域“赢”，功能越加越多。
- 没有人对整体体验负责，冲突被折中成平庸。
- 决策速度慢，反复推翻，团队无法形成稳定预期。

概念完整性不等于独裁。它要求**一个清晰的决策者 + 透明的决策依据 + 可被挑战的方案**，而不是“谁声音大听谁的”。

## 4. 第二系统效应：续作与新引擎最容易失控

### 4.1 第二系统效应

书里说，设计师的第二个系统往往是最危险的：第一个系统受资源/时间限制，第二个系统就想“把所有东西都做对”，于是过度设计、功能膨胀、结构复杂。

游戏项目的典型版本：

- 续作要“更大、更多、更开放”，同时换引擎、换管线、换美术风格。
- 新引擎要“一步到位”，把所有未来需求都预先抽象。
- 第二个项目想证明自己，于是每个系统都要“比前作更深”。

### 4.2 非目标清单

对抗第二系统效应，最有效的工具不是“更强的架构”，而是**明确不做什么**：

| 项目 | 非目标示例 |
| - | - |
| 续作 | 不做多人、不做开放世界、不换核心玩法 |
| 新引擎 | 不支持旧平台、不做通用编辑器、不追求所有渲染特性 |
| 新 IP | 不做大规模叙事、不做复杂经济、不做长期运营 |

非目标要写进文档、评审与排期，而不是只存在于主创的脑子里。

## 5. 沟通与文档：巴比伦塔为什么失败

### 5.1 项目工作手册

书里用巴比伦塔的失败说明：大型项目失败往往不是技术不行，而是**沟通与组织失败**。他提出“项目工作手册”：把规格、接口、决策、进度、变更集中到一处，让所有人看到同一份事实。

游戏项目需要类似的“单一事实来源”：

| 文档 | 主要读者 | 更新时机 |
| - | - | - |
| 游戏设计文档（GDD） | 设计/程序/美术/音频 | 核心玩法/系统变更时 |
| 技术设计文档（TDD） | 程序/TA/QA | 架构/接口/性能方案变更时 |
| 美术圣经/风格指南 | 美术/外包/市场 | 风格/资产规范变更时 |
| 音频设计文档 | 音频/设计/程序 | 交互/混音/事件变更时 |
| 决策记录（ADR） | 全体 | 每个不可逆决策 |
| 里程碑/风险清单 | 制作/管理层 | 每周/每个里程碑 |

### 5.2 口头决策必须落盘

书里提到电话日志、会议、形式化定义、多重实现等“贯彻执行”的方式。核心不是文档格式，而是**决策有没有被记录、被同步、被验证**。

游戏项目最常见的沟通事故：

- 会上说“这个功能砍掉”，但文档没改，程序还在做。
- 主创口头说“手感再重一点”，程序和动画各自理解不同。
- 外包按旧版风格指南制作，返工两周。

一个简单的规则：**任何会影响跨职能工作的决定，24 小时内写进单一事实来源，并标注影响范围。**

## 6. 预算、范围与原型

### 6.1 削足适履：预算是设计约束

书里用“十磅放进五磅的袋子”讲空间/规模约束：资源有限时，必须做取舍，数据表现形式本身就是设计的一部分。

游戏项目的预算不止内存：

| 预算 | 约束什么 | 常见后果 |
| - | - | - |
| 内存/显存 | 资产数量、纹理/模型精度 | 加载失败、降质、崩溃 |
| CPU/GPU | 同屏单位、特效、物理 | 掉帧、发热、续航 |
| 内容预算 | 关卡/剧情/资产数量 | 后期砍内容、质量不均 |
| 团队预算 | 人力/外包/时间 | 加班、延期、范围蔓延 |
| 运营预算 | 服务器/客服/更新 | 上线后无法持续 |

范围、时间、质量、成本四者不可能同时无限。**最诚实的做法通常是砍范围，而不是砍质量或让人加班。**

### 6.2 未雨绸缪：原型与增量

书里有一章叫“未雨绸缪：计划抛弃一个原型”。但 20 周年纪念版里，Brooks 自己修正了这一点：瀑布模型是错误的，**增量开发/渐进精化**更好；不是“先造一个再扔掉”，而是“先做一个能跑的最小版本，再逐步长大”。

对游戏项目：

- 用垂直切片验证核心玩法、美术风格、性能与管线。
- 原型代码可以扔，但不要把“原型”直接当产品。
- 计划变更，而不是假设需求不变。
- 每个里程碑都产出“可玩、可测、可评估”的东西。

### 6.3 没有银弹：工具不消除本质复杂度

《没有银弹》区分了“本质复杂度”和“次要复杂度”：工具、语言、引擎可以降低次要复杂度，但无法消除“把复杂概念变成清晰设计”的本质困难。

游戏项目里，引擎、编辑器、AI 工具、自动化管线都很重要；但它们不会自动解决：

- 核心玩法是否好玩；
- 美术风格是否统一；
- 跨职能沟通是否顺畅；
- 范围与预算是否匹配。

把工具当银弹，往往会得到“管线很先进、游戏不好玩”的项目。

## 7. 布鲁克斯后来修正了什么

20 周年纪念版的价值，不只是重复经典，而是作者自己承认哪些地方错了：

- **瀑布模型是错误的**：增量开发、渐进精化更符合现实。
- **信息隐藏是对的**：Parnas 的观点比作者原书更正确。
- **“计划抛弃一个原型”要修正**：应该计划让系统逐步长大，而不是造完再扔。
- **人就是一切**：流程/工具是次要的，人的能力、协作与动机才是关键。
- **构建 vs 购买**：成品软件/中间件可以节省成本，但会带来集成与依赖问题。

所以读《人月神话》不能停在“加人没用”这一句。它更像一本**关于复杂协作的清醒剂**：承认不确定性、保护概念完整性、把沟通成本算进计划、用增量而不是瀑布。

## 8. 给游戏项目的检查清单

- [ ] 项目是否有唯一的概念负责人/创意决策者？
- [ ] 关键路径上的任务是否可并行？加人前算过沟通与 ramp-up 成本吗？
- [ ] 里程碑是否有明确的“完成定义”，而不只是日期？
- [ ] 风险是否被公开记录，而不是“其他部分会赶上”？
- [ ] 是否有单一事实来源的 GDD/TDD/风格指南/决策记录？
- [ ] 跨职能决策是否在 24 小时内落盘并同步影响范围？
- [ ] 是否有明确的非目标清单，防止第二系统效应？
- [ ] 内存/性能/内容/团队预算是否被当作设计约束？
- [ ] 是否用垂直切片/增量开发验证，而不是等“全部完成”？
- [ ] 是否把工具/引擎/AI 当银弹，而忽略玩法与协作的本质问题？
- [ ] 是否用加班掩盖估算问题？小团队不等于无限加班。
